<p>先把结论摆出来：登录几乎不占带宽，真正吃掉流量的是文件上传和流式输出。所以"Claude 住宅 IP 要多大带宽"这个问题，答案取决于你拿它干什么，而不是取决于账号数量。这篇用一组对照实验回答：同一条线路、三个场景、连续七天，把每天的实际流量记下来，再换算成带宽规格。所有数字都是实测口径，你可以照着重跑一遍。</p>

<h2>一、实验设计：三个场景、同一条线路、连续七天</h2>
<p>线路选一条 10Mbps 独享静态住宅，出口在美西，客户端是同一台机器上的三个独立浏览器 profile 加一个命令行环境。三个场景分别是：A 只做登录与页面浏览，B 长对话加文件上传，C 纯 API 调用。每天固定时段跑，流量用服务商控制台的日用量减去前一日读数，误差控制在 5% 以内。</p>
<h3>为什么要分开测</h3>
<p>因为三者的流量模型完全不同。页面浏览是突发的小请求加静态资源，对话是低速率长连接，API 是高频率小包。混在一起测，得到的平均值对任何单一场合都没指导意义。分开测之后你会发现，同一小时里 A 用了几十兆，B 可能用掉几百兆，C 只用了几兆。</p>

<h2>二、对照组一：只做登录与会话维持</h2>
<p>单次登录的流量主要在首屏：HTML 加 JS 加样式加图标，首访 1.5 到 3MB，后续访问靠缓存降到 300 到 600KB。登录之后的会话维持几乎不耗流量，心跳请求每次不到 1KB，一分钟一次，一天下来不到 2MB。七天实测日均 42MB，其中六成花在首屏资源上。</p>
<h3>这一组的带宽需求</h3>
<p>峰值出现在首屏加载的三到五秒内，瞬时能到 3 到 5Mbps，但持续时间极短。所以带宽下限可以给到 2Mbps，只要能忍受首屏慢一点。如果你的使用只有登录和看文档，2Mbps 独享完全够，不需要为"高峰"买 20Mbps。</p>
<h3>延迟比带宽更影响体验</h3>
<p>这一组真正的痛点是 RTT。出口在美西、客户端在国内，往返延迟 150 到 220ms 是常态，首屏要串行发十几个请求，每个都吃一次 RTT，加起来就能感觉到卡。用 mtr -rw 出口IP 看丢包和抖动，抖动超过 30ms 就该考虑换线路而不是加带宽。</p>

<h2>三、对照组二：长对话加文件上传</h2>
<p>对话本身流量不大：一轮问答上行 20 到 60KB（取决于提示词长度），下行流式输出按每秒 3 到 8KB 计，回答三十秒大约 100 到 250KB。十轮对话控制在 2MB 以内。真正拉高用量的是附件：上传一个 5MB 的 PDF，加上重试和分片，实际消耗 6 到 8MB；一天传十个附件，用量就上到 70MB 以上。</p>
<h3>实测日均与峰值</h3>
<p>七天里 B 组日均 186MB，峰值出现在有批量上传的那天，单日 520MB。峰值小时的带宽占用大约 6 到 9Mbps，主要来自上传，而且是持续性的——一个 20MB 的文件在 5Mbps 上行下要传三十多秒。这里要注意上行带宽，很多住宅线路下行给 100Mbps，上行只有 5 到 10Mbps。</p>
<h3>这一组该买多大</h3>
<p>按每天二十个附件、每个平均 5MB 估，日流量约 120 到 160MB，月流量 4 到 5GB。带宽侧给到 10Mbps 上行比较舒服，5Mbps 能用但传大文件会等。如果经常传几十兆的文件，优先看上行而不是下行。</p>

<h2>四、对照组三：API 批量调用</h2>
<p>API 的流量模型最省：一次请求平均 4KB 上行，响应平均 12KB，千次调用大约 16MB。七天里 C 组日均 19MB，跑了两千多次请求，带宽占用基本在 1Mbps 以下。这一组的瓶颈不是带宽，是并发连接数和出口稳定性——连接建立多了，每次握手都吃 RTT，整体耗时反而比流量更值得关注。</p>
<h3>并发与带宽的关系</h3>
<p>十个并发、每个请求 12KB，理论瞬时只需要 1Mbps，但实际因为 TLS 握手和队头阻塞，连接数上到 50 以上时，延迟会明显上升。经验值是单 IP 保持 20 到 30 个并发连接比较稳，超了就用多 IP 分摊，而不是硬加带宽。</p>
<h3>脚本侧怎么省流量</h3>
<p>开 gzip 压缩（多数客户端默认开）、复用连接（curl 加 --keepalive，或直接用 requests 的 Session）、避免重复拉取相同资源。三项做完，同样的调用量能省两成到三成流量。计费按 GB 的服务商，这一项直接对应账单。</p>

<h2>五、把三组数据换成带宽规格</h2>
<p>换算口径：1Mbps 持续一小时约 450MB。按上面的日均 247MB 算，理论上一小时就能跑完，实际上分散在八小时里，平均占用不到 0.1Mbps。所以流量从来不是带宽的决定因素，峰值并发和文件体积才是。</p>

<h3>选规格的三条经验</h3>
<p>一是看上行，别只看下行；二是按高峰小时而不是日均来定，高峰能扛住就不卡；三是留 30% 余量给重试和协议开销。按这三条算出来的规格，通常比销售推荐的档位低一到两档，成本能省不少。</p>
<h3>什么时候该加带宽而不是换线路</h3>
<p>判断方法：用 speedtest 或 iperf3 直连测一次基准，再通过代理测一次，如果代理侧只有基准的一成，说明是线路带宽不足；如果两边都正常但页面还是慢，多半是 RTT 或丢包问题，该换线路。</p>

<h2>常见问答</h2>
<h3>一个账号日常用，1Mbps 的住宅 IP 够吗？</h3>
<p>答：如果不传文件，够用。首屏会慢一点，但对话是流式的，对带宽要求很低。传附件就会明显等待，建议至少 5Mbps 上行。</p>
<h3>流量计费和带宽计费有什么区别？</h3>
<p>答：流量按 GB 结算，用多少算多少；带宽按 Mbps 包月，跑不满也照收。轻量场景选流量计费便宜，长期跑批处理选带宽包月更划算。</p>
<h3>多个账号共用一条线路，带宽要翻倍吗？</h3>
<p>答：不用按人数线性翻倍。人不会同时满速，按"峰值并发数 × 单人峰值"估，再打七折比较接近实际。十个号共用 20Mbps 通常比十条 5Mbps 更省。</p>
<h3>流式输出卡顿是带宽不够吗？</h3>
<p>答：多数是 RTT 抖动或中间节点丢包，不是带宽。用 mtr 看每跳延迟，抖动大的那一段就是问题所在，换线路比加带宽有效。</p>
